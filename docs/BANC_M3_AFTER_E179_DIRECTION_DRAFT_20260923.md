# E179 이후: 신경 출력과 상태 의존 힘 전달을 구분

E179는 두 무발화 세포가 속한 RM tibia-flexor 전체 출력이0이라는 설명을 배제했다. 실제 출력은 다른 세 MN에서 만들어지며 저장 관절 명령까지 정확히 전달된다. 이 결과와 E175의 제한 readout 가족 배제를 함께 보면, 같은 감각 연결 증폭이나 무발화 세포의 억제 제거를 반복할 근거는 약하다. 전체 보행 개선은 여전히 미달이다.

다음 E180의 우선 설계 위치는 **신경/근육 활성에서 실제 관절 힘으로 전달되는 인터페이스**다. 먼저 현재 식과 실제 제공되는 관절 위치·속도·액추에이터 입력을 바탕으로, 길항근별 상태 의존 항이 현재의 위치 서보/강성 모델과 어떤 동작에서 구별되는지 정한다. 새 보행 실행이나 임의 힘 상수 fit에 앞서, 기존 단일 Fe–Ti Hill fixture와 전체 FlyBody 사이의 단위·부호·입력·저장/차단 계약을 확인해야 한다. 단일 관절 fixture의 성공은 전체 BANC 보행 성공이 아니다.

이미 있는 기능과 실패를 재사용한다. `flylab/c/rate_body.py`의 active_length는 절댓값 moment 합을 강성 신호로 만들고 위치 명령을1+s로 나눈다. `flylab/c/banc_mechanics.py:64-98`의 식은 K0*D−K0*(1+s)*(q−q0)−C*qdot이며 실측 길이 곡선이 없는 공학 모델이다. `docs/BANC_GAIT_QUALITY_GOAL_PLAN_20260912.md:209-216`의 M2-E24/E26에서 실제 slip 감소와 함께 진전 유지 실패가 기록됐다. 따라서 '활성 의존 강성 추가'는 새로운 대안이 아니다. 기존 joint angle/velocity/load proprioception도 이미 연결되어 있어 '감각이 없다'고 설명해서는 안 된다.

`flylab/c/muscles.py`는 접촉·신경 연결이 없는 고정 몸체/왼쪽 경골의 두 Hill 근육 fixture다. 움직이는 여섯 다리의 BANC 경로에서 길항근별 실제 길이·속도 의존 힘을 계산하는 구현·시험은 이번 한정된 source/기록 검색에서는 발견하지 못했다. 전체 저장소의 모든 과거 시도를 조사했다는 뜻은 아니다. `motor_recruitment.py`의 reference torque balance도 움직이는 보행 관절 상태를 받는 runtime 힘 모델과 구별한다.

E180 설계에서 다음을 고정해야 한다.

1. 현재 고정 moment/position 식과 이미 기각된 active_length를 명시적 comparator로 삼는다. E179의 양·음 명령 합이나 E165의 아래쪽 기하 부호만으로 결함을 확정하지 않는다. E166 대응 전진 표본에서도 같은 부호가 관측됐다.
2. 구별할 새 항은 해당 근육의 길이·수축 속도 또는 이에 대응하는 관절 상태에 따른 힘 전달이다. 좌우/보행 위상·시각·교사 궤적·목표 방향을 운동 생성기로 쓰지 않고, BANC 노드/연결/근육 소유와 최종 motor cut을 유지한다. 휴식 자세를 직접 덮어쓰거나 root 힘으로 보행을 보완하지 않는다.
3. 새 식이 필요한 상태 변수를 현재 몸체에서 측정할 수 있는지, 단일 관절 fixture의 source 단위·moment arm을 전체 다리에 전용할 수 있는지 먼저 확인한다. 근거 없는 다른 다리 padding이나 임의 Hill 계수 채택을 하지 않는다. 신경/몸체 경로에 넣기 전에 부호·수동성/에너지·상한·저장 미래·차단·기존 복원을 생성 자료로 검산한다.
4. 실제 차이를 구별하는 최소 대조와 보행 F3–F5 개발 진입 조건을 사전 확정한다. 근육 수준 합격을 최종 보행 성공으로 올리지 않는다. 원래 F6 자세와6목표 F7은 여전히 미노출/미완료이며 성공 후보가 있을 때 원래 계약대로 평가한다.

E180은 방향 초안이다. 세부식/소스 gate/freeze/새 원본 값 분석/모델·신경·물리·fit 실행은 아직0이다. 현재 누적3423.920152800041/3656초를 승계하며 필요한 배정을 설계에서 명시한다. 이전 실패나 자원을 새 이름으로 초기화하지 않는다. 부모 설계 → actual gpt-6-sol(소스 계약 검토 medium, 새 힘 전달 구현 high 또는 xhigh) → 부모FIRST → 같은 Sol첫수정 → 부모SECOND/잔여 직접 수정의 사용자 작업 방식을 유지한다. 전체 목표 active, F1–F8 미완료, M2/UI/F6 보존이다.
