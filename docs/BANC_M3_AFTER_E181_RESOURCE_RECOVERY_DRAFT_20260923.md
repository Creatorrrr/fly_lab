# E181 자원 중단 이후 재검증 초안

E181의 bounded optimizer 구현과 zero-theta native 재현은 확인됐다. LF 사전 step8개는 startup 보호를 통과하지 못했다. LM plus는 startup과1.415초의 기록 건강성을 통과했지만 시간 한도 때문에3초 평가가 완성되지 않았다. 보행 가설은 not-tested이며 실패를 성능 기각으로 바꾸지 않는다. LM minus 및 나머지4축은 미실행이다.

다음 사전 계약은 **방법 변경 없이 같은 LM 후보를 자원이 준비된 상태에서 다시 판정하는 기술 복구**로 좁힌다. 별도 local image queue client가 LM 시작0.732초 뒤 시작해 실행 구간과 겹쳤다. 현재 기록만으로 지연 인과를 확정하지 않는다. 원본 E181 source/freeze/결과와 실패 cost를 보존하며 같은 output을 덮어쓰지 않는다.

1. 실제 살아 있는 기존 queue client PID16248/35496 및 http://127.0.0.1:8188/queue의 running/pending 개수를 다시 조회한다. 이전 PID·파일만으로 busy/idle을 단정하지 않는다. queue가 비고 해당 작업이 종료된 것을 확인하기 전에는 새 CUDA 원본을 시작하지 않는다. 다른 프로젝트 작업을 종료하거나 설정을 바꾸지 않는다. 장시간 기다려야 하면 CPU 설계·구현만 진행하며 현재 goal을 active로 둔다.
2. 고정 모델/입력/평가기/3초 길이/초기99 보호/실제CUDA 및100/105/110초 한도는 유지한다. 새3초 baseline을 source와 raw prefix로 재현한 뒤, 이미 사전 선택된 LM plus(.125)와 minus(-.0625)를 동일zero 중심에서 비교한다. 순서·기울기·목적함수·합격 문턱을 시간 초과 결과에 맞춰 바꾸지 않는다. 새로운 팔은 새로운 명시적 복구 계약과 source review로 실행하며 기존 E181 gate를 위조하거나 monkeypatch하지 않는다.
3. 후보 선택은 원래 E181의 J·원래baseline hard constraints·1% 최소 개선 및 고정 tie-break를 유지한다. 후속 LH/RF/RM/RH 순회는 기술적으로 유효한 두 LM 결과와 부모 raw 리뷰 뒤 별도로 구체화한다. 작은J 개선도 원래3초 개발 진입이나 최종F1–F8을 대신하지 않는다. startup 실패·물리적 실패·자원/기술 오류를 구분한다.
4. 새 driver에는 실행 전 공유 GPU 작업 확인과 native 실행 중 자원 관측을 기록한다. 한 시점의 GPU 이용률만으로 유휴 상태를 판단하지 않는다. 기존 신경/물리/평가 소스는 재사용하고 계측 때문에 신경/물리 상태를 바꾸지 않는다. 부모 설계→gpt-6-sol의 난이도별 effort 첫 구현→부모FIRST→같은Sol 첫수정→부모SECOND/잔여수정을 유지한다.
5. 기존 보수누적3697.5422548998613/4994초를 승계한다. 최초 복구3팔을 각110초, 총330초로 예약해도 기존 배정 안이다. 전체 원본 모델 시도 횟수에 실패한 E181 후보도 포함한다. 추가 예산·자동재시도·한도 증액을 이 초안으로 만들지 않는다. 재차 자원 오류가 나면 측정된 원인·실제 live handle을 확인하고 동일 자동 재시도를 하지 않는다.

현재는 초안이며 복구 source 구현·freeze·source gate·새 원본 실행0이다. 이 방향의 목적은 중단된 후보의 실제 보행 효과를 분명히 판정하고 원래 최적화로 돌아가는 것이다. M2/UI/F6와 유효/invalid 과거 증거, 원래 동일후보 F1–F8을 유지한다.
