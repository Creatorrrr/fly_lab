# 실제 과학 실행을 독립된 작은 계약으로 연결하는 설계

목적은 기존 F1–F8의 실제 BANC 보행을 검증하는 것이다. 현재 E360 실행 구조 복구는 실제 Ruff를 통과했지만 scanner의 재귀·JSON0 타입·remaining 연산 순서에서 반복해서 실패했다. 마지막 실제 실패5.153초를 포함한 closed118/68calls/31passes와 비용·Source·collector·소유권0을 보존했다. 이 실패를 통과로 바꾸거나 같은 호출을 재실행하지 않는다. 과학 배열·CUDA·신체는 아직 이 단계에서 실행하지 않았다.

현재 접근의 문제는 새 과학 모듈 자체와 관계없는 역사 실행 관리 코드의 검증이 실제 신체 계산의 선행 조건이 된 것이다. 기존 E360 fixture/suite/Q는 미통과 상태로 남기고, 이를 사용하지 않는 새 과학 실행 계약을 검토한다. 이것은 그 검사를 통과했다고 선언하거나 과거 Original20 권한을 승계하는 방식이 아니다. 기존 코드와 실패 증거를 보존하고 새 경로의 필요한 직접 검증을 실제 수행한다.

새 경로는 이미 실제 Astra S1–S3를 반영해 Sol이 구현 중인 startup-ray 모듈을 대상으로 한다. ROOT FIRST·같은 Sol sole R1(필요 시)·ROOT SECOND를 마친 뒤 Source 스냅샷을 봉인한다. 실제 lint와 작은 numerical unit tests, 실제 stdlib pre-array/admission의 source/input/grant/offset·worker1 검사, timeout/실패 후 ownership 종료·once accounting을 직접 검증한다. 유효한 결과가 나오기 전 metadata true 선언으로 qualification을 발급하지 않는다. 실제 GPU 연산의 수치 대응·raw audit·body의 native 관측은 해당 역할의 직접 결과로 판정한다.

별도 실제 Original+6000 grant는 기존 누적·stage 비용을 유지하며 global16200/stage6300/new-local6000과 발급 시 debit offset을 묶는다. shared Original 동시성은 기존 lock을 재사용하고 동일 host의 다른 Original 작업이 있으면 실행하지 않는다. 생성 검증 비용과 원본 비용을 구분해 기록하되 기존118 비용을 삭제·재분류·초기화하지 않는다. 역할 예약은120/1200/120/300/300/120/120/180=2460이며 필요한 audit/close를 예약한다. 외부 실제 도구 dispatch부터 최종 반환까지 once 비용을 기록하고 내부 종료 시간이나 합성 결과로 대신하지 않는다.

처음에는 새 executor의 작은 생성 실패/종료 검증과 Source·수치 단위 검증을 실제 시행한다. Original 접근은 grant/admission의 모든 직접 조건이 준비된 뒤 packet 감사→ray→후보 감사→neutral/candidate 각1개 연속0→99→300→raw/body 감사 순서다.
